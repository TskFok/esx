# 计划 03：状态保存与索引表受控验证

## 复现方法与边界

在仓库根目录运行 `node scripts/performance-state-and-cluster.mjs`。脚本从 Git 提交 `0f840bd644552c16a3c6aac48be51889953c6cb6` 读取原组件与原存储实现，用 Vite 已安装的 esbuild 在项目 `node_modules` 下创建临时 bundle 并在退出时清理；当前版本读取工作树源码。每项预热 3 次，随后串行采样 12 次。CPU 数值取 `process.cpuUsage()` 的 user + system 时间，单位毫秒，p95 取升序第 `ceil(0.95 × 12)` 项。

索引样本分别为 1,000 和 10,000 个公开索引；组件用 React `renderToStaticMarkup` 完成默认首页 SSR，并统计 `<tbody>` 中的 `<tr>`。这只验证同步服务端渲染与输出行数，不代表浏览器 DOM、布局、绘制、滚动帧耗时或 React Profiler 提交耗时。基线组件源码取指定提交，组件导入的其他共享模块使用当前工作树版本；因此 CPU 数值是受控组件对照，不是整仓库历史构建对照。

保存样本在两个版本各自初始化存储后，连续提交 20 次草稿内容变更；模拟数据还包含 200 条无响应快照的已保存请求。基线调用真实历史 `writeAppStorage` 20 次；当前版本使用真实 `createPersistQueue` 合并 20 个 `hot` 更新，`flush()` 后调用当前 `writeAppStorage`。`LazyStore` 通过 esbuild 在内存中替换为只记录 `set`、`save` 调用与 `set(value)` 的 JSON UTF-8 字节数的 Fake Store。CPU 时间覆盖整批异步 JavaScript 调用，但不包含真实 Tauri IPC、磁盘写入、持久化格式、系统钥匙串或自动保存调度；这里的 `save` 是模拟方法的调用次数，不可解释成文件落盘次数。
